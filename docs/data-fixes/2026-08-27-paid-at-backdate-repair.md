# 2026-08-27 — Repair paid_at month attribution for backfilled payments

Task 1 of the financial-correctness program. `paid_at` on ~140 historical
`deal_payments` rows (and a small cluster of `expenses` rows) recorded when
staff clicked "mark paid" during a bulk backfill session, not when the client
actually paid — so `accounting_ledger_v` / `pl_summary_for_range()` (which
key on `coalesce(paid_at::date, start_date)`) attributed the income/expense
to the wrong month, mostly dumping everything into June–August 2026 instead
of spreading it across the real service periods back to late 2025.

Reference case: deal `000205` (ΓΑΒΡΙΗΛΙΔΗΣ ΜΠΑΝΤΑΒΑΣ), web_dev €322.58 net,
service period starting 2026-04-02, was paid around that date but `paid_at`
was stamped `2026-08-06 09:02:15`. Before the repair its income was invisible
in April; after, it appears there as it should.

## Rule applied (same convention autopay already uses)

```sql
update public.deal_payments
   set paid_at = start_date::timestamptz
 where status = 'paid' and paid_at::date > start_date + 30;

update public.expenses
   set paid_at = start_date::timestamptz
 where status = 'paid' and paid_at::date > start_date + 30;
```

`paid_at` is set to midnight UTC on `start_date` — attributing the row to the
period month, exactly like `ensure_recurring_payments`/`ensure_recurring_expenses`
already do for freshly-seeded rows. The `deal_payments_recompute_job_dates`
trigger only reacts to `status`/`start_date`/`end_date` changes while
`status='paid'` — it does not fire on a bare `paid_at` update, so no
`jobs.period_due_date` moved. Verified: 0 `jobs` rows had `updated_at` change
during the run.
